# 微信自动化讨论进度

记录时间: 2026-04-20

## 当前目标

希望实现一个实验性能力:

- 监控 Windows 版微信中的消息
- 当别人发送指定消息后, 以尽可能快的速度自动发送一条或连续多条指定消息
- 优先考虑精确触发, 包括文本、表情包等条件

## 已确认的环境前提

- 当前项目工作区: `D:\flutter_app\super_ivan_pro`
- 当前微信版本: `4.1.7`
- 当前需求重点: 不是泛化机器人, 而是高精度、高速度的规则触发回复

## 已讨论出的关键结论

### 1. WeChatFerry 不适合作为当前主路线

原因:

- WeChatFerry 更适合微信 `3.9.x` 一带
- 当前环境是微信 `4.1.7`
- 对 `4.x` 直接采用 Hook/注入路线的兼容性和风险都更高

结论:

- 不建议把 WeChatFerry 作为当前版本微信的首选方案

### 2. 纯 UI 自动化在微信 4.x 上存在明显限制

主要问题:

- 群聊中发送者身份信息很多时候不是可直接访问的文本 UI
- 群成员昵称在部分场景下需要截图 + OCR 才能识别
- UI 结构变动频繁, 不同小版本可能导致监听或点击失效
- 对"指定人触发"这类要求, 稳定性不足

结论:

- `pywechat` / `wx4py` 这类方案更适合做界面控制和消息发送
- 不适合单独承担高精度消息判定逻辑

### 3. 如果目标是"别人发了指定文本后立即回复", 更适合走底层监听

优选思路:

- 用微信 `4.x` 本地数据库或消息层做实时监听
- 用 UI 自动化负责最终发送动作

这样做的好处:

- 识别文本消息不依赖 OCR
- 匹配速度更快
- 规则更容易做成"群 + 发送人 + 内容 + 冷却时间 + 连续发送"

## 候选技术路线

### 路线 A: 底层监听 + UI 发送

这是当前最推荐的实验路线。

建议组件:

- 监听: `ylytdeng/wechat-decrypt`
- 备选监听: `L1en2407/wechat-decrypt`
- 发送: `wx4py`
- 备选发送: `pywechat`

推荐理由:

- `wechat-decrypt` 明确支持微信 `4.x` 本地数据库解密和实时消息监听
- 其代码和说明中对消息类型有明确映射, 包括:
  - `1 = 文本`
  - `47 = 表情`
- 适合做"指定文本命中后立刻触发"
- `wx4py` 明确提到已测试 `4.1.7.59`

### 路线 B: 纯 UI 自动化

候选项目:

- `Hello-Mr-Crab/pywechat`
- `claw-codes/wx4py`

适合场景:

- 监听某个会话
- 检测到普通消息后执行自动回复
- 做快速验证和原型

不足:

- 精度受 UI 结构影响
- 小版本升级容易破坏定位
- 对发送人识别、表情精确识别不够稳

## 关于不同触发条件的当前判断

### 文本触发

最可行。

推荐规则:

- talker = 指定群或指定联系人
- sender = 指定发送人, 可选
- type = 文本
- content = 精确匹配 / 包含匹配 / 正则匹配
- 命中后发送一条或多条消息

### 表情包触发

可做, 但分两种:

- 如果是文本形式表情, 可直接按文本匹配
- 如果是微信自定义表情或商店表情, 更适合走底层监听

原因:

- `wechat-decrypt` 对 `type 47 = 表情` 有明确支持
- README 中还提到表情包内联显示以及 `emoticon.db` 映射

结论:

- "任意表情包出现就触发" 比较可行
- "特定表情包出现才触发" 理论上也可做, 但需要继续确认表情标识字段的稳定性

### 指定人 + 指定消息触发

这是最难但仍值得继续验证的方向。

当前判断:

- 纯 UI 自动化不稳
- 如果底层监听结果里能稳定拿到 `sender` 或 `senderName`, 这条需求就更接近可落地
- `chatlog` 的 webhook 配置样例中已经出现了 `sender` 字段, 说明这类路线是有希望的

## 目前最值得继续推进的实验方案

### 最小实验目标

实现:

1. 监听指定聊天对象
2. 当出现指定文本时立即触发
3. 自动连续发送 1 到 N 条预设消息
4. 支持去重, 避免重复触发
5. 支持冷却时间, 避免短时间重复响应

### 建议规则模型

```yaml
rule:
  talker: "目标群或联系人"
  sender: "可选, 目标发送人"
  type: 1
  match_mode: exact
  content: "指定触发词"
  reply_to: "same_chat"
  messages:
    - "第一条回复"
    - "第二条回复"
  cooldown_ms: 800
  dedupe_by: "seq"
```

## 当前主要风险

### 风险 1: 微信 4.1.7 的兼容性波动

- `pywechat` 已有针对 `4.1.7` 的监听问题反馈
- UI 侧栏、会话搜索、消息监听等定位都可能因小版本变化而失效

### 风险 2: 发送速度瓶颈不在检测而在界面操作

即使监听很快:

- 切换会话
- 激活输入框
- 粘贴消息
- 点击发送

这些都可能成为最终延迟来源。

### 风险 3: 去重和连发策略处理不当会导致误触发

需要防止:

- 同一条消息反复命中
- 连续多条回复被重复执行
- 历史消息回放时再次触发

## 下一步建议

按优先级建议如下:

1. 先验证 `wechat-decrypt` 在当前微信 `4.1.7` 上能否稳定看到新文本消息
2. 再验证能否拿到足够稳定的 `talker` / `sender` 信息
3. 发送侧优先尝试 `wx4py`, 因其对微信 `4.x` 版本支持更明确
4. 首个实验先只做:
   - 指定聊天对象
   - 指定文本
   - 单条自动回复
5. 验证通过后再扩展:
   - 连续多条回复
   - sender 过滤
   - 表情触发
   - 冷却时间和去重

## 当前阶段结论

当前最合理的技术判断是:

- 想在微信 `4.1.7` 上做"尽量精确且尽量快"的触发回复
- 最适合的是"底层监听 + UI 发送"混合方案
- 纯 UI 自动化只适合作为发送层和补充验证层
- 第一优先级不是继续扩展需求, 而是先验证底层监听在当前版本上的稳定性
