# 微信自动化实现计划

记录时间: 2026-04-20

## 说明

- `superpower` skill 不在当前会话可用技能列表中
- 本计划按普通工程方式制定
- 当前阶段只做方案确认, 不直接开工实现

## 最终目标

实现一个实验性自动化系统:

- 监听 Windows 微信 `4.1.7`
- 当目标聊天中出现指定触发条件时
- 以尽可能低的延迟自动发送一条或多条预设消息

优先级:

1. 先做好"指定文本触发"
2. 再扩展"指定人过滤"
3. 最后再扩展"指定表情触发"

## 总体架构

采用两段式方案:

### 1. 监听层

职责:

- 实时接收微信新消息
- 抽取消息字段
- 执行规则匹配
- 生成发送任务

建议技术:

- 首选: `wechat-decrypt`
- 备选: `chatlog`

选择理由:

- 更适合微信 `4.x`
- 更适合做低延迟文本匹配
- 不依赖 UI OCR 识别文本

### 2. 发送层

职责:

- 打开或切换目标聊天
- 将预设消息发送出去
- 控制连续发送节奏
- 记录发送结果

建议技术:

- 首选: `wx4py`
- 备选: `pywechat`

选择理由:

- `wx4py` 对微信 `4.x` 的支持更明确
- 更适合只做发送动作

## 第一版范围

第一版只做最小可用闭环:

- 监听 1 个目标聊天
- 触发条件仅支持文本
- 触发后发送 1 到 N 条文本
- 支持去重
- 支持冷却时间
- 支持测试模式

第一版暂不做:

- OCR
- 表情精确匹配
- 多规则并发
- GUI
- 复杂管理后台
- 自动回复图片/文件

## 实现阶段

### 阶段 0: 技术验证

目标:

- 在当前机器上验证 `wechat-decrypt` 是否能稳定看到新消息
- 验证 `wx4py` 是否能稳定发消息到指定聊天

输出:

- 一份本机可行性验证记录
- 一份最小测试脚本

通过标准:

- 能捕获目标聊天的一条新文本消息
- 能成功发送一条测试消息到目标聊天

### 阶段 1: 监听适配器

目标:

- 抽象统一的新消息结构

建议数据结构:

```json
{
  "seq": "唯一序列",
  "time": "时间戳",
  "talker": "聊天对象ID或名称",
  "talkerName": "聊天对象显示名",
  "isChatRoom": true,
  "sender": "发送人ID",
  "senderName": "发送人显示名",
  "type": 1,
  "content": "消息文本",
  "raw": {}
}
```

输出:

- `watcher_adapter`
- 原始事件转标准消息对象

### 阶段 2: 规则引擎

目标:

- 支持最小规则匹配

建议规则结构:

```yaml
rules:
  - id: demo_rule
    enabled: true
    talker: "测试群"
    sender: ""
    type: text
    match_mode: exact
    pattern: "开始"
    cooldown_ms: 800
    replies:
      - "收到"
      - "第二条"
```

第一版支持字段:

- `talker`
- `sender`
- `type`
- `match_mode`
- `pattern`
- `cooldown_ms`
- `replies`

匹配模式:

- `exact`
- `contains`
- `regex`

### 阶段 3: 去重与冷却

目标:

- 避免同一条消息重复触发
- 避免短时间多次响应

建议机制:

- 基于 `seq` 做去重
- 基于 `rule_id + talker + sender + pattern` 做冷却

输出:

- 去重缓存
- 冷却控制器

### 阶段 4: 发送调度器

目标:

- 将规则命中结果变成实际发送动作

建议设计:

- 单队列串行发送
- 每条消息之间保留小间隔
- 失败重试次数可配置

建议发送参数:

```yaml
send:
  inter_message_delay_ms: 180
  retry: 1
  switch_chat_before_send: true
```

### 阶段 5: 日志与回放

目标:

- 便于定位误触发和漏触发

建议日志分类:

- `watcher.log`
- `match.log`
- `send.log`
- `error.log`

建议记录内容:

- 收到的原始消息
- 匹配命中的规则
- 发送结果
- 失败原因

### 阶段 6: 表情扩展

目标:

- 在文本触发跑稳后, 再加入表情触发

扩展思路:

- 先支持 `任意表情(type=47)` 触发
- 再确认是否可以拿到稳定的表情唯一标识
- 如果拿不到稳定标识, 再考虑截图比对或降级为"任意表情触发"

## 性能目标

第一版不追求极限, 追求稳定:

- 检测延迟: 尽量接近实时
- 总体触发到发送: 目标控制在 1 秒级以内
- 连发多条消息: 每条间隔 150ms 到 300ms

## 风险与限制

### 风险 1

- `wechat-decrypt` 这类方案需要读取进程内存或解密本地数据库
- 环境要求更高

### 风险 2

- 发送层仍然依赖 UI 自动化
- 微信前台状态和窗口焦点可能影响发送速度与稳定性

### 风险 3

- 如果后续要加入"指定人 + 指定表情"双重匹配, 复杂度会明显上升

### 风险 4

- 误触发会造成重复发消息
- 必须先做测试群验证

## 开工顺序

我建议按下面顺序推进:

1. 先做 `watcher_probe`
2. 再做 `sender_probe`
3. 再做最小规则引擎
4. 再做串行发送队列
5. 文本触发跑稳后再扩展 sender 过滤
6. 最后扩展表情触发

## 我建议的确认结论

为了最快开工, 我建议先锁定为:

- 只支持一个目标聊天
- 只支持文本触发
- 不做 sender 过滤
- 支持连续发送多条固定文本
- 采用独立 Python 模块实现
- 监听走 `wechat-decrypt`
- 发送走 `wx4py`

这样可以最快做出第一版闭环。
