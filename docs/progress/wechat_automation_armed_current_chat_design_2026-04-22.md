# WeChat Automation Armed Current-Chat Design

Saved at: 2026-04-22
Status: approved discussion snapshot for the next implementation stage

## 1. 背景

我们在上一阶段已经验证了两件核心事实：

1. `wechat-decrypt` 可以低延迟拿到真实消息历史，并且当前 `START` ->
   `TEST` / `第二条` 的 dry-run 流程已经跑通。
2. 基于 `wx4py` 的“按联系人/群名搜索目标再发送”路径虽然可作为后续方案，
   但现阶段不适合作为第一优先级实现。

当前需要解决的问题已经明确变成：

- 不是先解决“表情包精确识别”
- 不是先解决“任意联系人/群聊后台精准投递”
- 而是先实现：
  - 一旦检测到指定触发消息，就立刻在当前聊天框发送指定消息
  - 这个能力必须可以手动启动 / 手动停止
  - 这个能力可以设置触发次数上限，或者设置为无上限
  - 达到次数上限后，自动停用，不再继续触发，必须人工重新启动

## 2. 为什么上一条 real-send 看起来会先退出微信再重新进去

这不是我们额外写的“先关闭再打开微信”逻辑，而是 `wx4py` 自身连接流程的一部分。

本地已验证到的 `wx4py` 逻辑是：

- `WeChatClient(auto_connect=True)` 会立即执行 `connect()`
- `connect()` 会先检查并修复辅助功能环境
- 如果发现注册表 `RunningState` 原值是 `0`，`wx4py` 会认为必须重启微信，
  让辅助功能树重新生效
- 然后它会重新查找窗口、尝试恢复窗口、必要时还会处理登录页上的
  “进入微信”按钮

所以之前看到的“微信先退出再进入”，本质上是：

- `wx4py` 为了连上可操作的 UIA 控件树，触发了它自己的重连/重启流程

这也是为什么当前阶段不应该把“按目标搜索并发送”作为主路径：

- 连接动作重
- 会拉起微信窗口
- 会和用户当前鼠标操作互相干扰
- 对“立刻发出”这个目标不够友好

## 3. 方案比较

### 方案 A: 按目标名称搜索后发送

定义：

- 监听到触发消息后
- 再去按联系人/群名搜索目标
- 然后把消息发过去

优点：

- 理论上可以不依赖当前聊天框
- 未来更适合做“后台指定对象发送”

缺点：

- 发送前还有一段搜索/定位动作
- `wx4py` 连接阶段会激活甚至重启微信
- 群名带 emoji、备注名变化、搜索命中歧义时会不稳定
- 不是当前“最快速度”目标下的最优路径

结论：

- 暂时降级为后续能力，不作为下一阶段主线

### 方案 B: 当前聊天框极速发送

定义：

- 由操作者先手动打开目标聊天
- 系统进入“已武装 / armed”状态
- 一旦检测到触发消息，直接向当前聊天输入框发送预设回复

优点：

- 不需要临时搜索目标
- 发送路径最短
- 更符合“检测到就立刻发”的目标
- 行为边界简单，便于先做稳定版本

缺点：

- 依赖当前聊天框已经被操作者准备好
- 如果用户在武装期间把焦点切到别的软件，存在误发风险
- 需要额外加前台窗口保护和手动启停机制

结论：

- 这是当前推荐方案，也是下一阶段实现主线

### 方案 C: 继续先做表情包/复杂匹配

定义：

- 优先做表情包识别、复杂内容识别、群成员精确识别等能力

优点：

- 长期能力更强

缺点：

- 触发识别复杂度高
- 现在真正卡住的不是“能不能识别更多类型”，而是“识别后如何最快发出去”
- 容易把当前阶段做散

结论：

- 暂缓，不作为下一实现阶段

## 4. 当前锁定方案

### 4.1 核心模式

下一阶段只做一个主模式：

- `armed_current_chat`

这个模式下：

- 监听器继续使用现有 `wechat-decrypt` live watcher
- 匹配器继续负责判断“是否命中指定规则”
- 发送器不再执行“搜索目标 -> 发送”
- 而是直接面向“当前已经打开的聊天框”发送

### 4.2 手动启停

需要新增一个明确的运行态：

- `disarmed`：停用，不响应触发
- `armed`：启用，允许响应触发

行为规则：

- 默认建议 `disarmed`
- 只能人工切换到 `armed`
- 只能人工主动 `disarm`
- 若达到触发次数上限，也要自动切回 `disarmed`

这相当于给系统增加一个“实验开始 / 实验结束”的总闸门。

### 4.3 触发次数

每条规则或者每次武装会话，至少需要支持下面两种模式：

- `max_triggers = N`
- `max_triggers = unlimited`

建议解释为：

- 每成功触发一次完整回复批次，记作 1 次
- 当累计次数达到 `N`，自动停用
- 自动停用后，不允许再次触发，直到操作者手动重新启动

这样最符合你描述的：

- “触发指定次数之后就不会再触发第二次”
- “需要我们手动启动”

### 4.4 当前聊天框发送

这里的“当前聊天框发送”需要明确成：

- 不按联系人名搜索
- 不切换到别的聊天
- 不做跨聊天路由
- 只向当前已经准备好的那个聊天输入框发消息

这意味着操作者需要先完成：

1. 手动打开目标聊天
2. 确认当前聊天框正确
3. 再手动启动 automation

然后系统才进入真正可触发状态。

### 4.5 连续消息

回复消息仍然允许保持现在的多条结构，例如：

1. `TEST`
2. `第二条`

建议语义保持为：

- 一次命中
- 执行一整个 reply batch
- batch 内按顺序连续发出

后续只需要单独调优：

- 两条消息之间的间隔
- 是逐条回车发送，还是一次性拼接发送

## 5. 必须补上的保护规则

为了避免再次出现“切到别的软件导致误发”的问题，当前方案必须把保护规则一起带上。

### 5.1 前台窗口保护

发送前至少校验：

- 当前前台窗口是不是微信
- 当前聊天输入控件是否可用

如果不满足：

- 本次不发送
- 记录失败日志
- 不要把内容误打到其他软件

### 5.2 手动武装视为一次性授权

你之前要求：

- 如果要发送消息，先问你

这个要求在“人工测试单次发送”阶段完全合理。

但在“自动监听后立刻发送”的正式实验模式里，不能每次触发都再弹出确认，
否则就失去自动化意义。

因此新的边界建议定义为：

- 平时默认不允许自动发送
- 只有当操作者手动点击“启动 / arm”后，才视为本轮实验期间允许自动发送
- 一旦手动停止或自动达到上限，则授权结束

这样可以把“安全边界”和“自动化速度”同时保住。

### 5.3 命中去重

当前已有 dedupe 能力仍然要保留。

原因：

- `wechat-decrypt` 是轮询历史
- 如果不做去重，同一条消息可能在多个轮询周期内重复命中

所以新的 armed 模式，不是替换 dedupe，而是：

- dedupe + armed state + max trigger count

一起工作。

## 6. 下一阶段暂缓项

以下内容明确暂缓：

- 表情包精确匹配
- 发送前按联系人/群名搜索目标
- 后台自动切换聊天
- 复杂群成员级别判定
- 多规则大规模并发

理由很简单：

- 当前最重要的是把“检测后立刻在当前聊天框发出”做稳定
- 先把最短路径打通，再扩展复杂目标

## 7. 推荐的下一实现边界

下一阶段实现边界建议锁定为：

1. 保留现有 live watcher
2. 新增 `armed` 运行态
3. 新增 `max_triggers` / `unlimited`
4. 新增“当前聊天框发送”发送器
5. 发送前增加“微信前台窗口保护”
6. 先只支持文本触发
7. 先只支持文本回复

只要这一版稳定，后面再分支做：

- 表情包匹配
- 命名目标发送
- 更强的群聊/私聊识别

## 8. 当前结论

你的设计方向是对的，而且比“先做复杂识别、再按目标搜索发送”更适合当前阶段。

推荐结论如下：

- 当前优先方案：`armed_current_chat`
- 当前优先目标：命中后立即在当前聊天框发送
- 当前必要控制：手动启停 + 次数上限 + 前台窗口保护
- 当前暂缓项：表情包匹配、命名目标发送、复杂目标路由

这份文档写入后，后续实现应以这份设计为准，不再继续把“按目标搜索后发送”
当作当前第一优先级。
