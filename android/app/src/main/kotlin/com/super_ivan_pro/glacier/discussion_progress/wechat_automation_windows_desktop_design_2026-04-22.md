# WeChat Automation Windows Desktop Design

Saved at: 2026-04-22
Status: awaiting final user approval before implementation

## 1. 目标

这一版要解决的核心问题不是“自动化能力不够”，而是“当前原型可以跑，但测试和使用太麻烦”。

第一版桌面版要达成的目标是：

1. 只面向 `Windows`。
2. 用一个 `Flutter Windows` 桌面程序统一承载现有自动化能力。
3. 让操作者尽量接近“双击即用”，不再手动分别拉起多个脚本。
4. 在桌面端直接完成：
   - 启动/停止全部后台服务
   - 选择监听对象
   - 配置触发规则和回复
   - 切换 `普通模式 / 极速模式`
   - `armed / disarmed`
   - 查看实时日志、最近事件和错误状态
5. 继续复用已经验证成功的 Python 自动化主链路，而不是重写整个底层。

## 2. 非目标

第一版明确不追求以下内容：

1. 不做跨平台。
2. 不把全部自动化逻辑重写成 Dart。
3. 不优先做复杂表情包识别、多联系人并发路由、后台切换聊天等能力。
4. 不优先做非常花的界面，先把“统一、可用、可打包、好测试”解决掉。

## 3. 方案比较

### 方案 A: Flutter 只做前端壳，继续直接调用散落脚本

定义：

- Flutter 只做按钮和页面
- 每个按钮直接拉起现在已有的 Python 脚本
- `wechat-decrypt`、bot、控制接口仍然是多个散进程

优点：

- 第一眼实现快

缺点：

- 后台职责继续分散
- Flutter 层会很快变成脚本调度器
- 后面做状态同步、错误恢复、打包都会更乱

结论：

- 不推荐作为第一版正式桌面结构

### 方案 B: Flutter 桌面壳 + 统一本地服务进程

定义：

- Flutter 负责界面和交互
- 后台由一个统一的本地服务进程负责托管
- 本地服务再去管理 `wechat-decrypt`、bot、配置和日志
- Flutter 只和这一层统一 API 通信

优点：

- 能继续复用当前 Python 主链路
- UI 与自动化能力边界清楚
- 后面加“监听对象面板、模式切换、日志面板、打包分发”都会更顺
- 更接近真正的软件，而不是“脚本工具集合”

缺点：

- 比直接调用散脚本多一层整理工作

结论：

- 这是推荐方案，也是当前锁定方案

### 方案 C: 直接把核心迁到 Flutter / Dart / Windows 原生

定义：

- 尽量不保留当前 Python 主链路
- 重新在 Dart 或 Windows 原生侧做监听、规则与发送

优点：

- 长期形态最统一

缺点：

- 第一版会明显变慢
- 会打断当前已经验证成功的原型积累

结论：

- 暂不适合作为第一版

## 4. 当前锁定架构

第一版锁定为：

- `Flutter Windows 桌面端`
- `Python 统一后台服务`
- `现有 wechat_automation Python 核心`
- `wechat-decrypt`

总体数据流为：

`Flutter UI -> 本地服务 API -> 自动化核心 -> WeChat / wechat-decrypt`

### 4.1 Flutter Windows 桌面端

职责：

1. 提供中文界面。
2. 显示服务状态、模式状态、armed 状态。
3. 配置监听对象、规则、回复、模式参数。
4. 查看最近事件、触发记录、发送记录和错误日志。
5. 一键启动/停止全部后台服务。
6. 发起 `arm / disarm` 操作。

Flutter 不直接和散脚本打交道，只通过统一 API 和服务层交互。

### 4.2 Python 统一后台服务

职责：

1. 作为 Flutter 唯一依赖的本地服务入口。
2. 启动和监控 `wechat-decrypt` 子进程。
3. 启动和监控 bot 子进程，或直接在服务进程内托管 bot 循环。
4. 管理桌面版自己的配置文件、状态文件和日志文件。
5. 暴露统一的本地 JSON API 给 Flutter。
6. 在桌面端统一处理错误、重启、健康检查和状态同步。

建议实现形态：

- 新增一个本地服务进程，例如 `wechat_automation_service`
- Flutter 只负责拉起/停止这一层
- 这一层再去托管 `wechat-decrypt` 和 bot

### 4.3 现有自动化核心

继续复用的内容：

1. live watcher
2. 规则匹配
3. armed / disarmed
4. trigger budget
5. 当前聊天发送
6. 日志写入

第一版不去推翻已经跑通的链路，而是在服务层和桌面层做收口。

## 5. 打包策略

第一版目标是尽量接近“真正双击即用”。

因此打包策略建议为：

1. Flutter 产出 Windows 桌面应用。
2. Python 后台服务不依赖用户手动安装 Python。
3. 后台服务打成桌面程序可携带的独立运行产物。
4. `wechat-decrypt` 作为桌面包内置资源，由后台服务托管启动。

推荐打包形态：

- `Flutter Windows app`
- `bundled python service executable`
- `bundled wechat-decrypt runtime assets`

这样用户层面的体验会变成：

1. 打开桌面程序
2. 点击“启动全部服务”
3. 在一个窗口里配置和测试

而不是继续手动进入多个目录执行多个命令。

## 6. 本地状态与配置

桌面版不应继续依赖仓库里的实验配置文件作为长期运行位置。

第一版建议迁到 Windows 本地用户目录，例如：

- `%LOCALAPPDATA%\\SuperIvanPro\\wechat_automation\\config\\`
- `%LOCALAPPDATA%\\SuperIvanPro\\wechat_automation\\logs\\`
- `%LOCALAPPDATA%\\SuperIvanPro\\wechat_automation\\runtime\\`

原因：

1. 打包后不能假设用户仍在源码目录运行。
2. 配置应该和安装目录解耦。
3. 日志、armed 状态、规则配置应该随用户环境持久化。

建议持久化内容：

1. 当前监听对象
2. 规则列表
3. 普通/极速模式
4. 模式参数
5. armed 状态
6. 上次服务启动状态
7. 最近日志位置

## 7. 第一版首页结构

第一版不建议拆复杂导航，先做单页控制台。

首页分成 5 个区块：

### 7.1 服务状态区

显示：

1. WeChat 检测状态
2. `wechat-decrypt` 运行状态
3. bot 运行状态
4. armed / disarmed
5. 当前模式：普通 / 极速

操作：

1. 一键启动全部服务
2. 一键停止全部服务
3. 一键 arm
4. 一键 disarm

### 7.2 监听对象区

第一版同时支持两种方式：

1. 最近会话点选
2. 手动输入名称

这里的“最近会话”不依赖未知新接口，优先使用现有历史数据聚合出最近活跃对话列表。

显示：

1. 当前监听对象名称
2. 对话类型：私聊 / 群聊
3. 最近刷新时间
4. 最近活跃列表

### 7.3 规则配置区

第一版先保留最核心字段：

1. 触发文本
2. 匹配方式：精确 / 包含 / 正则
3. 回复消息列表
4. 最大触发次数
5. 冷却时间

### 7.4 模式配置区

这一块用于切换：

1. 普通模式
2. 极速模式

并同时显示对应说明，避免把模式差异隐藏成神秘开关。

### 7.5 日志与事件区

显示：

1. 最近收到的消息事件
2. 最近触发记录
3. 最近发送记录
4. 最近错误日志

这块在第一版里很关键，因为它直接解决“现在到底哪里没生效”的问题。

## 8. 监听对象方案

用户已经明确要求第一版同时支持：

1. 最近会话点选
2. 手动输入名称

这意味着服务层需要维护“当前激活监听对象”的统一定义。

建议行为：

1. 第一版只允许一个当前监听对象生效。
2. 桌面端选择后，服务层把它保存为 `active_target`。
3. watcher 和规则层都优先使用这一对象。

建议对象结构至少包含：

1. `talker`
2. `display_name`
3. `chat_scope`
4. `is_group`

## 9. 模式定义

第一版同时支持两种模式。

### 9.1 普通模式

目标：

- 优先稳定

行为：

1. 使用保守轮询
2. 允许自动查找输入框
3. 保留较稳妥的等待时间
4. 允许更完整的恢复逻辑

适用场景：

- 日常运行
- 希望降低误发和焦点问题

### 9.2 极速模式

目标：

- 优先速度

行为：

1. 将 watcher 轮询压到极低值
2. 优先只请求当前激活监听对象的消息
3. 默认用户已经打开目标聊天
4. 默认输入框已经聚焦
5. 发送时不再执行完整输入框搜索/恢复逻辑
6. 将发送前后的 sleep 压到最低

适用场景：

- 实验场景
- 用户愿意自己保证聊天正确且焦点正确

### 9.3 UI 中必须明确展示的风险提示

切换到极速模式时，桌面端必须显式展示：

1. 当前聊天必须已打开
2. 输入框必须已聚焦
3. 若焦点丢失，可能发送失败
4. 若聊天窗口准备错误，可能发错地方

## 10. 极速模式的具体设计

当前原型之所以“命中后要等几秒”，主要耗时点是：

1. watcher 轮询间隔
2. 每次发送前重找输入框
3. `wx4py` 保守的 sleep

因此极速模式必须不是“把现有参数稍微改小一点”，而是单独走一条更短的发送路径。

### 10.1 watcher

极速模式下建议新增参数：

1. `rapid_poll_interval_ms`
2. `rapid_history_limit`
3. `rapid_target_only`

默认建议：

1. `rapid_poll_interval_ms = 20`
2. `rapid_target_only = true`

如果已设置监听对象，则 watcher 在极速模式优先按该对象拉取历史，而不是全局拉取后再过滤。

### 10.2 sender

极速模式下建议新增一个更直接的发送路径，例如：

- `focused_fast_send`

核心语义：

1. 直接信任当前焦点就是目标输入框
2. 若当前焦点不是可编辑输入框，则快速失败
3. 不执行完整的自动查找与恢复
4. 使用最短发送链路

这条路径的目的不是“兜底修复”，而是“最快发出”。

### 10.3 sleep 压缩

极速模式下建议压缩这些等待：

1. 两条消息之间的 `inter_message_delay_ms`
2. 输入框准备前后的 sleep
3. Enter 发送后的额外等待

建议语义：

- 普通模式保留恢复性等待
- 极速模式只保留必要的最小等待

### 10.4 快速失败原则

极速模式不做强恢复，只做快速失败。

也就是说：

1. 聊天不对 -> 失败
2. 输入框没聚焦 -> 失败
3. 前台不是微信 -> 失败

失败要记录清楚，但不要为了“自我修复”再去消耗额外时间。

## 11. 服务 API 草案

Flutter 与服务层的接口，第一版建议至少包含：

1. `GET /status`
   - 当前服务状态
   - WeChat 状态
   - wechat-decrypt 状态
   - bot 状态
   - armed 状态
   - 当前模式

2. `POST /services/start`
   - 启动全部服务

3. `POST /services/stop`
   - 停止全部服务

4. `GET /targets/recent`
   - 获取最近活跃对话列表

5. `POST /targets/active`
   - 设置当前监听对象

6. `GET /rules`
   - 获取当前规则

7. `POST /rules`
   - 保存规则

8. `POST /arm`
   - 进入 armed

9. `POST /disarm`
   - 进入 disarmed

10. `POST /mode`
    - 切换普通/极速模式

11. `GET /events/recent`
    - 最近事件

12. `GET /logs/recent`
    - 最近日志

第一版不要求把所有历史数据都做复杂查询，只要先把当前测试闭环打通。

## 12. 错误处理与恢复

### 12.1 普通模式

普通模式允许有一定恢复逻辑：

1. 输入框自动查找
2. 发送失败可重试
3. 服务状态异常时给出提示

### 12.2 极速模式

极速模式只保留最小保护：

1. 前台必须是微信
2. 焦点必须是输入框
3. 监听对象必须已设置

不满足就直接失败并写日志，不做重操作恢复。

### 12.3 后台服务层

服务层负责：

1. 子进程存活检测
2. 启动失败日志
3. 健康检查
4. 向 Flutter 回传明确错误信息，而不是让 UI 猜测

## 13. 测试策略

第一版建议分三层测试：

### 13.1 Python 单元测试

覆盖：

1. 模式参数解析
2. 监听对象配置
3. 普通模式 / 极速模式的行为分流
4. 极速模式快速失败规则

### 13.2 本地集成测试

覆盖：

1. 服务启动/停止
2. Flutter 与服务 API 通信
3. 状态持久化

### 13.3 Windows 人工验证

覆盖：

1. 桌面端一键启动全部服务
2. 监听对象点选
3. 手动输入监听对象
4. 普通模式完整触发
5. 极速模式完整触发
6. armed / disarmed 生效
7. 触发上限后自动停用

## 14. 风险与当前判断

### 风险 1: 极速模式更脆

这是预期内风险，不是设计错误。

处理方式：

- 在 UI 中明确说明前提条件
- 通过普通模式和极速模式并存来管理风险

### 风险 2: `current_chat_probe.py` 不能作为唯一真相

这一点已经在当前实验中观察到：

- 它可能记录 success，但未必真的出现在聊天历史中

因此桌面版的验证真相仍应以：

1. bot 日志
2. WeChat UI
3. `wechat-decrypt` 历史

共同判断。

### 风险 3: `wechat-decrypt` 打包与托管复杂度

这是第一版最实际的工程风险之一。

处理方式：

- 把它放在统一服务进程托管下
- 不让 Flutter 直接感知它的复杂细节

## 15. 当前结论

这版桌面化方案已经锁定为：

1. 只做 Windows
2. Flutter 做桌面壳
3. Python 做统一后台服务
4. 一键托管全部后台服务
5. 监听对象支持“最近会话点选 + 手动输入”
6. 第一版同时支持普通模式和极速模式
7. 极速模式通过“目标过滤 + 焦点假设 + 最小等待 + 快速失败”实现
8. 打包目标是尽量接近双击即用

这份文档确认后，下一步再进入实现计划，不在当前阶段提前写代码。
